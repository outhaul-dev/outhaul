# SSO Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let people sign in to Outhaul through any OIDC provider, next to passwords. This is part 2 of 3 and needs part 1 (`2026-11-02-accounts-roles.md`).

**Architecture:** A small `internal/sso` package wraps OIDC discovery, the authorization code flow and token verification behind a `Provider` interface that tests can fake. A system admin stores the provider in Settings, with the client secret sealed. The first sign-in creates an account with no role, keyed by issuer and subject.

**Tech Stack:** Go 1.26, `github.com/coreos/go-oidc/v3`, `golang.org/x/oauth2`, both pure Go.

**Spec:** `docs/superpowers/specs/2026-11-02-sso-roles-protected-routes-design.md`

## Global Constraints

- Test first. Commits look like `feat(scope): summary`, and every commit message ends with `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`.
- The UI always says "SSO", never a provider's name. The button reads exactly `Sign in with SSO`.
- Use `go-oidc` for verification. No hand-written JWT checks.
- The client secret is sealed, added to `sealedQueries`, and never shown again.
- Scopes are exactly `openid email profile`, with PKCE, `state` and `nonce`.
- SSO sessions on the Outhaul host last 8 hours. Password sessions keep `sessionTTL` (7 days).
- No new `OUTHAUL_*` settings. SSO needs the existing `OUTHAUL_PUBLIC_URL`.
- Every new route goes in `routes()` with a level. A new public route is also added to `TestPublicRoutesAreExactlyThese`, and a new path wildcard to the value map in `TestEveryRouteRefusesTheWrongPeople` (both in `internal/server/access_test.go`).
- The server keeps no record of a sign-in in progress. Anyone can start one, so a bounded list could be emptied by a stranger, which would stop everyone else's SSO sign-in.

## Review Focus

- A callback arrives with a forged, replayed or missing `state`, or the state cookie is gone: the login page shows a "try again" error with the password form, not a 500. Pinned in Task 3.
- The provider is down at sign-in: the login page shows an error and the password form still works. Saving unreachable settings is refused. Pinned in Tasks 2 and 3.
- The provider returns neither `email` nor `preferred_username`: sign-in is refused with a clear message and no account is created. Pinned in Tasks 1 and 3.
- Someone types an SSO person's email into the password form, or a password account tries to use an `sso:` username: refused. Pinned in Task 3.
- An admin changes the issuer, or leaves the secret blank when saving: an issuer change needs confirmation and ends SSO sessions; a blank secret keeps the stored one. Pinned in Task 2.

### Task 3: Signing in

**Files:**
- Create: `internal/server/sso_login.go`
- Modify: `internal/server/auth.go`, `internal/server/routes.go`, `internal/server/server.go`, `internal/server/account.go`, `internal/server/templates/account.tmpl`, `internal/server/templates/login.tmpl`, `internal/server/users.go`, `internal/server/templates/users.tmpl`, `internal/store/users.go`, `internal/server/templates/noaccess.tmpl`
- Test: `internal/server/sso_login_test.go`, `internal/store/users_test.go`

**Interfaces:**
- Consumes: `ssoProvider`, `sso.Fake`.
- Produces:
  - `(*Store) FindOrCreateSSOUser(ctx, issuer, subject, email string) (core.User, error)`: username is `"sso:" + issuer + "|" + subject`, role `none`, email refreshed on every call
  - `const ssoSessionTTL = 8 * time.Hour`
  - `type ssoFlow struct { State, Nonce, Verifier, Return string; Expires time.Time }`, carried in the flow's own cookie as base64url JSON, for 10 minutes. The server stores nothing.
  - `const ssoStateCookiePrefix = "outhaul_sso_"`: one cookie per flow, named with the first 12 characters of its state, so two tabs signing in at once don't break each other
  - `func encodeSSOFlow(f ssoFlow) string`, `func decodeSSOFlow(v string) (ssoFlow, bool)`
  - Routes at `levelPublic`: `GET /auth/sso/start`, `GET /auth/sso/callback`

`ssoFlow.Return` stays empty in this plan. Part 3 uses it, and checks it again at the callback, because a person can edit their own cookie.

- [ ] **Step 3: Implement**

`/auth/sso/start` generates state, nonce and an `oauth2.GenerateVerifier()` verifier, and sets that flow's cookie holding the encoded flow (`HttpOnly`, `SameSite=Lax`, `Path=/auth/sso`, 10 minutes, `Secure` from `requestIsHTTPS`). The callback finds the cookie named from `state`, decodes it, compares its `State` with the query's in constant time, checks `Expires`, and clears the cookie whatever the outcome. The provider accepts a code once, and the cookie is gone after the first callback, so a replay has nothing to use. Errors redirect to `/login?error=<code>`, and `handleLoginForm` maps codes to fixed messages: never reflect provider text into the page. `s.login` takes its TTL from the account: `ssoSessionTTL` for SSO, otherwise `sessionTTL`. Keep `validateCredentials`' refusal of `sso:` usernames from part 1.
